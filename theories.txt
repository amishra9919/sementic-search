5. Pgvector's Cosine distance operator (<=>):

compare two vector using cosine similarity in pgvector --> SELECT '[1,0,0]'::vector <=> '[1,0,0]'::vector;
examples: SELECT '[1,0,0]'::vector <=> '[-1,0,0]'::vector; 
            think of it           [0,1]
                                    ↑
                                    |
                        [-1,0] ←----+----→ [1,0]
            The angle is 180°, therefore:
            cos(180°) = -1
            cosine similarity = -1
            cosine distance = 1 - cosine similarity (even logically the dist looks like 2 units)

8. Creating HNSW index :

a. query
    CREATE INDEX documents_embedding_hnsw_idx ON documents
    USING hnsw (embedding vector_cosine_ops);

    USING hnsw --> Use pgvector's HNSW index method.
    embedding vector_cosine_ops --> means indexing the embedding column for cosine-distance operations.

=> this will be used whenever we'll do vector search

b. why vector_cosine_ops ? ==> to use same metrix 
PostgreSQL generally cannot use that HNSW index for the cosine-distance query if hnsw is creating another method 

    Suppose we have:

    A = [some vector]
    B = [some vector]
    C = [some vector]
    ...

    When HNSW builds its graph, it needs to make decisions like:

    Which vectors are neighbors?

    A should connect to whom?
    B should connect to whom?
    C should connect to whom?

    To answer that, it needs a definition of:

    distance(A, B)

    If we selected:

    vector_cosine_ops

    then those neighbor/search decisions use cosine-distance semantics.

c. Other operations for operator index 

(operator class)    Method 
----------------------------------
vector_cosine_ops	Cosine
vector_l2_ops	    Euclidean/L2	
vector_ip_ops      	Inner product

We're creating an HNSW index on embedding, configured with pgvector's cosine operator class,

9. Does PostgreSQL actually use our HNSW index?

    -->PostgreSQL's query planner chooses an execution plan based on estimated cost.
    -->Uses the HNSW in Vector search 

    for small rows like 10 rows it might now use the hnsw index 

    SELECT id, content FROM documents
    WHERE embedding IS NOT NULL
    ORDER BY embedding <=> '[...]'
    LIMIT 5;

    for this query this might fetch result using 2 ways
        Option A

        Sequential Scan
        → examine rows
        → calculate distances
        → sort
        → top 5

        Option B
        HNSW Index Scan
        → navigate HNSW
        → obtain nearest candidates
        → top 5

        Option A may actually be cheaper. Navigating an index has overhead tojust for less no of columns.

12. ts_rank vs BM25:

    a. ts_rank gives a document proportionally better on repeting words 
    b. it dosent focus on the importance  

    BM25 essentially thinks:

    database (appears in 800,000 documents) → "Very common word. Not a strong signal."

    PostgreSQL (appears in 100,000 documents) → "More specific. Give it more importance."

    pgvector (appears in 2,000 documents) → "Very rare and specific. Give it even more importance."

    c. ts_rank does not mean PostgreSQL searches only one document.

        Suppose your table has 1,000 documents and the query is:

        "PostgreSQL database"

        First, PostgreSQL full-text search finds all documents that match:

                            QUERY
                    "PostgreSQL database"
                            |
                            ↓
                    Search whole table
                            |
            ┌──────────────┼──────────────┐
            ↓              ↓              ↓
        Doc 5          Doc 27         Doc 800
        MATCH          MATCH           MATCH

        Your WHERE condition does this:

        WHERE to_tsvector('english', content)
            @@ plainto_tsquery('english', 'PostgreSQL database')  #GIN index used here

        So yes, it searches across your whole collection (and a GIN index can make finding those matches much faster).

        Then comes ranking.

        Let's say 50 documents matched. PostgreSQL needs to decide:

        Which matching document should be result #1, #2, #3...?

        That's where ts_rank comes in.

13. BM25 v GIN Index

    1. How do I find documents containing a term?
                    ↓
                INDEXING

    2. How relevant is each document?
                    ↓
                RANKING

    3. In what order should I return them?
                    ↓
                SORTING

    A GIN index helps PostgreSQL efficiently locate matching full-text-search entries.

    BM25 is a ranking function.

14. BM25 is corpus-dependent. (MAIN DISTINCTION )

        Suppose our documents are:

        D1: PostgreSQL database indexing
        D2: PostgreSQL vector database
        D3: PostgreSQL relational database
        D4: Dogs and cats

        Across this corpus: PostgreSQL appears frequently.

        But: indexing appears rarely.

        Therefore "indexing" can carry more discriminative information.

        """
        Now imagine we insert another million documents.
        The statistics of the corpus change.
        """

        That's fundamentally different from embeddings.

        An embedding for: "PostgreSQL database indexing" is produced by the embedding model based on that text/model. 
        It doesn't need to inspect every other document in your database before producing the vector.
